> この記事は _Smart Endpoints and Dumb Pipes_ および _Decentralized Governance_ の観点から Arachne の実装判断を整理します。エンドポイントの知性を Java / Spring の文脈で正しく実装するために、どの設計判断が必要だったかを記録します。

## なぜ Arachne を作ったか

Python 版の Strands Agents SDK を Java + Spring Boot の業務システムに持ち込もうとしたとき、いくつかの障壁があります。

まず言語の壁。Python の async/await モデルと Java のスレッドモデルは根本的に異なります。Python 版がそのまま動く JVM ラッパーはありません。

次に Spring との統合。Spring Security のスレッドコンテキスト、Micrometer によるメトリクス収集、Spring Session による永続化、`@Bean` による DI ── これらは Spring エコシステムの中で初めてスムーズに機能します。外部ライブラリをそこに接続するアダプターを自前で書くコストは、移植を書くコストと大差ありません。

そこで Python 版を**行動仕様のリファレンス**として扱い、Java に移植したのが Arachne です。コアフローの `Agent → EventLoop → Model / Tool` は Python 版と同じ考え方を踏まえていますが、実装は Java と Spring に合わせて書き直しています。

## blocking runtime という選択

最初の設計判断は「同期 blocking runtime を基本にする」ことです。

Python 版は async を前提としていますが、Spring MVC / Spring Boot の業務アプリケーションは多くの場合、同期リクエスト処理モデルで書かれています。Servlet スレッドが処理を完結させ、レスポンスを返す、というモデルです。ここに async/reactive を混在させると、Spring Security のスレッドローカルコンテキスト伝播や、既存のトランザクション境界と噛み合わなくなります。

エージェントの `run` メソッドは blocking で最終回答を返します。内部でツール呼び出しのループを回しますが、呼び出し元スレッドはその完了を待ちます。ストリーミングは blocking runtime の上に追加的に乗せた構造です。ストリーミング API はエージェントが内部で LLM レスポンスをチャンク単位で処理しながらイベントをコールバックに渡し、最終的には通常の結果を返します。ストリーミングを使わない既存のコードは一切影響を受けません。

この設計を採用したのは「sync ユーザーを reactive や streaming の経路に強制しない」という原則からです。

## セッション管理 ── Spring Session に乗る

エージェントをマルチターン会話に対応させるには、会話履歴をリクエストをまたいで保持する必要があります。HTTP サーバーでは 1 リクエストごとに新しいエージェントインスタンスが作られるため、状態の保持はインスタンスの外に出さなければなりません。

Arachne のセッション管理は `SessionManager` インターフェースで抽象化されています。Spring Session のセッションリポジトリが検出されれば自動的に Spring Session バックエンドを使い、そうでなければインメモリのデフォルトを使います。Spring Session の Redis 実装を依存に追加するだけで、会話履歴が Redis に永続化されます。food-delivery-demo ではこれが既定値であり、Redis が常にセッションストアです。

セッションに保存されるのは、メッセージリスト・エージェント状態・保留中の interrupt リストです。エージェントは `run` の冒頭でセッション ID が設定されていれば前回の状態を復元します。

## interrupt ── human-in-the-loop の仕組み

エージェントは実行途中で一時停止することができます。停止した状態はセッションに永続化されます。HTTP 経路では「一時停止してレスポンスを返し、次のリクエストで再開する」という使い方を想定しています。order-service の 4 ステップワークフローはこの仕組みを使っており、各ステップの間でユーザーの確認を待ちます。

セッションをまたいで interrupt が保持できるため、「今日注文を中断して、明日再開する」という使い方も可能です。

## 未解決のコーナー ── interrupt + structured output

現状で意図的に未解決のままにしているコーナーケースがあります。

**structured output を指定した実行中に interrupt が発生したとき**です。

interrupt が起きると、エージェントは中断状態をセッションに保存します。resume 後はツール結果を送り返してループを続けます。通常のテキスト出力であれば問題ありません。

しかし、特定の出力型を指定した呼び出しの場合、「どの型で structured output を取り出すべきか」という型付きの invocation メタデータがセッションには保存されていません。セッション復元後に resume しても、出力型の情報が失われています。

現時点での回避策は、interrupt を使うフローでは型指定なしの呼び出しを使い、resume 後に structured output が必要なら型安全でない方法で取り出すというものです。

food-delivery-demo の 4 ステップワークフローは、interrupt を使う各ステップを独立した呼び出しに分け、structured output は各ステップの末尾でのみ取り出す設計にしているため、このコーナーケースを回避しています。

## 意図的な deferred

interrupt + structured output の問題を解決するには、セッション保存時に型付きの invocation メタデータも含める必要があります。ただし、この変更はセッションのシリアライゼーションスキーマに影響するため、後方互換性の扱いが必要です。

この課題は意図的に deferred にしています。food-delivery-demo の範囲では現状の回避策で十分であり、より一般的なユースケースが具体化するまで設計を固定しないことを選んでいます。

**設計の判断を deferred として記録する**ことそれ自体も、ひとつのベストプラクティスです。「後で解決する」という意思決定は、「今は解決しない」という積極的な選択です。未解決の問題を放置しているのではなく、解決の条件を明示して保留しているという違いは、チームの認識と文書化に影響します。Arachne の未解決コーナーはこの考え方で整理されています。
